What's actually in this repo's AI-DLC folders

Two directory trees, two different jobs. .claude/ is the framework — the reusable engine, the same in every AI-DLC project. aidlc/ is this project's own record — every decision, question answered, and artifact this specific build produced. This maps every folder in both — and, inside each one, every one of the 304 individual .md files with its own one-line purpose. Click any collapsed group to expand it.

.claude/ — the framework aidlc/ — this project's record

01 · The core distinction

One is code you didn't write. One is a transcript of everything you decided.

Delete .claude/ and copy it back in from a fresh AI-DLC install — nothing project-specific is lost, because nothing project-specific lives there. Delete aidlc/ and you've lost the entire history of this build: every requirement, every reviewed design, every generated file's manifest, every question you were asked and how you answered it.

.claude/ — the framework

Shipped, version-identical across every AI-DLC project

  • The orchestrator logic and stage definitions
  • 11 domain-expert agent personas + 2 reviewers + 1 composer
  • The methodology knowledge each agent reads before acting
  • The engine — 71 TypeScript tools that track state, log decisions, compile the stage graph
  • Automated hooks and quality sensors

aidlc/ — this project's record

Unique to this build; this is what you'd show someone to explain what happened

  • The affirmed team practices (testing posture, layering rules, deploy policy)
  • Every requirement, design doc, and review verdict this project actually produced
  • The full audit trail — every decision logged, every question and its answer
  • Traceability files linking requirements → design → code → tests
  • One folder per piece of work ("intent") — this build has two

You describe what you want, or run a skill

Either typed freeform, or a specific command like /aidlc-code-generation to run one stage directly.

2

The orchestrator decides what runs next

Reads the live state and the compiled stage graph, returns exactly one instruction — never improvised.

.claude/tools/aidlc-orchestrate.ts + tools/data/stage-graph.json

3

The right stage file and persona load

The stage's own file says what it needs and who leads it; that agent's full persona and knowledge load into context.

.claude/aidlc-common/stages/<phase>/<stage>.md + .claude/agents/<role>-agent.md

4

Every relevant rule from this project's memory loads too

So the output is consistent with every decision already made — not just what this one stage happens to know.

aidlc/spaces/default/memory/*.md

5

Questions get asked, an artifact gets written, a gate opens

You approve, request changes, or the loop repeats. Every question and answer, every gate decision, gets logged.

aidlc/spaces/default/intents/<intent>/<phase>/<stage>/*.md

6

Hooks and sensors run automatically underneath all of it

Nothing above has to remember to log an event or check a requirement — that's handled without being asked.

.claude/hooks/*.ts + .claude/sensors/*.md

05 · One real stage, walked through

What Code Generation actually left behind

This is the real, on-disk output of one stage from this build — not a hypothetical. Every file here exists in this repo right now.

aidlc/spaces/default/intents/260917-meeting-card-scheduler/ └─ construction/code-generation/ ├─ code-generation-plan.md # the 12-step build plan, approved before a line of code was written ├─ code-generation-questions.md # the Plan Approval Q&A that gated it ├─ unit-test-instructions.md # what "done, tested" meant for this stage ├─ code-summary.md # what got built, key decisions, deviations disclosed ├─ source-manifest.json # all 56 generated files, indexed └─ traceability.json # every requirement mapped to the code that satisfies it

Every other stage in this build left the same kind of trail — its own folder, its own questions file, its own produced artifacts. That's the whole of what aidlc/ is: 20-odd folders like this one, chained together by traceability files that point backward to the requirement that justified them.

06 · Terms worth knowing before you brief someone

Glossary

Stage
One unit of work with a defined lead, inputs, and outputs — e.g. "NFR Design." 33 exist; a given project runs some subset of them.
Phase
A group of stages — Ideation, Inception, Construction, Operation (plus a bootstrap-only Initialization).
Scope
A named profile deciding which stages run and how deep — "mvp" runs 23 of 33; "poc" runs 8. This build used a custom composed scope tailored to its exact requirements.
Intent
One tracked piece of work, with its own folder under aidlc/spaces/<space>/intents/. A workspace can hold several; only one is "active" at a time.
Gate
An approval checkpoint — nothing advances past one without an explicit human decision.
Directive
The single instruction the orchestrator returns each time it's asked what happens next.
Agent persona
The role Claude adopts for a stage — e.g. "developer agent" for Code Generation, "architect agent" for Domain Design.
Space
A top-level grouping under aidlc/spaces/ — most setups only ever use one, named "default."
