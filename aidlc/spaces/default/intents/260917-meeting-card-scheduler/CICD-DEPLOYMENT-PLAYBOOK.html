Reference playbook

The standard CI/CD pipeline, start to finish

Six phases, 27 concrete steps — from a pre-commit hook on your own machine to a bake-time monitor after production traffic hits the new build. Not every project needs all 27; the comparison at the bottom shows exactly which ones this project has and which a bigger SaaS would add.

PHASE A

Before code leaves your machine

The cheapest place to catch a mistake is before it's ever pushed. One step, but it saves everyone downstream real time.

1

Pre-commit hooks

blocking

Runs locally on git commit: lint, formatter check, and a fast secret scan. Catches the embarrassing stuff before it's even proposed.

Huskylint-stagedgitleaks protectpre-commit

PHASE B

Continuous Integration — every pull request

Everything here runs automatically the moment a PR opens or updates. This is where "vulnerability check" and "secret check" actually live for most teams.

2

Checkout + install dependencies

automatic

Cached so it's fast on every run — this is the baseline every other step depends on.

actions/checkoutactions/setup-nodenpm ci
3

Lint / static style analysis

blocking

Catches style violations and common bug patterns (unused vars, unsafe equality, etc.) before a human ever looks at the diff.

ESLintRuffgolangci-lint
4

Type check

blocking

For a typed language, a clean type-check is cheap insurance against a whole category of runtime bugs.

tsc --noEmitmypy
5

Unit / component tests + coverage floor

blocking

The core correctness gate. A coverage floor (commonly 70–85%) stops it from silently eroding over time.

VitestJestpytest
6

Secret scanning

blocking

Scans the PR diff for API keys, passwords, and tokens. Independent of the pre-commit hook — catches what a contributor's local hook wasn't installed to catch.

GitleaksTruffleHogGitHub secret scanning
7

SAST — static application security testing

blocking (Critical/High)

Scans your own source for vulnerability patterns — injection risk, unsafe deserialization, path traversal — without running the code.

CodeQLSemgrepSnyk Code
8

Dependency vulnerability scan

blocking (Critical/High)

Checks every package you depend on against known-CVE databases. This is the single highest-value check for most apps — most real vulnerabilities ship in via a dependency, not your own code.

npm auditSnykDependabot alertspip-audit
9

License compliance scan

optional

For a SaaS you intend to sell or keep closed-source, checks that no dependency's license (GPL, AGPL) legally obligates you to open-source your own code.

FOSSAlicense-checker
10

Build verification

blocking

Does the production build actually succeed? Cheap to run, and it catches "works in dev, breaks in build" every single time.

next buildwebpackdocker build
11

Integration tests

blocking

Tests real boundaries — a real (ephemeral) database, a real queue — instead of mocks. Usually the slowest CI step, so it's worth isolating from the fast unit-test loop.

Testcontainersdocker-compose in CI
12

Container image build + scan

optional — if containerized

Builds the actual image you'll ship and scans its OS-level packages for known vulnerabilities, not just your app dependencies.

TrivyGrypeDocker Scout
13

Infrastructure-as-Code validation

optional — if using IaC

Lints and security-scans your Terraform/CDK/CloudFormation before it's ever applied — catches an open security group before it's live, not after.

checkovtfseccfn-lint
14

Human code review + required approvals

gate

Branch protection makes every check above a required status — nothing merges with a red check, and at least one human has to actually approve the diff.

GitHub branch protectionCODEOWNERS

PHASE C

Merge & release prep

What happens the moment code lands on main — turning a commit into a releasable, traceable artifact.

15

Merge, auto-tag, changelog

automatic

Squash-merge keeps history linear; a version bump and changelog entry get generated from the commit messages, not written by hand.

semantic-releaseConventional CommitsChangesets
16

Build the release artifact, generate an SBOM, sign it

automatic

One immutable, versioned build — a container image, a compiled binary, a static bundle — pushed to a registry. The SBOM (Software Bill of Materials) and signature are what let you prove, months later, exactly what shipped and that it wasn't tampered with.

Docker registrycosignsyft

PHASE D

Deploy to staging / preview

The dress rehearsal — verify the exact artifact that will go to production, in an environment that behaves like production.

17

Auto-deploy to staging

automatic

No human step — every merge (or every PR, for preview environments) gets its own live URL automatically.

Vercel PreviewKubernetes namespace per PRHeroku Review Apps
18

E2E / smoke tests against staging

blocking (to promote)

Real browser, real network calls, the full user journey — this is what catches the bugs unit tests structurally cannot see (a misconfigured CSP header, a broken third-party integration).

PlaywrightCypress
19

Performance tests + DAST

optional, blocking if run

Load-tests key endpoints against real latency/throughput budgets, and DAST attacks the running app the way a real attacker would — different from SAST, which only reads source.

k6Lighthouse CIOWASP ZAP
20

Accessibility + visual regression

optional, usually non-blocking

Automated a11y scanning and screenshot-diffing against the last known-good UI — cheap signal, rarely worth blocking a release over.

axe-corepa11yPercyChromatic

PHASE E

Production release

The highest-stakes phase — everything here is designed around one question: how do we ship without a bad deploy taking users down?

21

Manual approval gate

gate — or skip if CD-mature

A named person clicks "promote." Teams with strong test coverage and observability sometimes graduate to skipping this — every merge auto-deploys to prod — but that's a deliberate, earned decision, not a default.

GitHub Environments (required reviewers)
22

Database migrations

blocking, handle with care

The single riskiest step in the whole pipeline. Migrations must be backward-compatible with the currently running code (additive columns, never a rename-and-drop in one step) because old and new code run side-by-side during a rolling deploy.

Prisma MigrateFlywayAlembic
23

Deploy via the chosen release strategy

automatic

Rolling (replace instances gradually), blue/green (switch traffic to a fully-new fleet at once), or canary (send 5% of traffic first, watch, then ramp) — the choice depends on your traffic volume and risk tolerance, not a universal default. Feature flags decouple "deployed" from "visible to users," so a risky change can go out dark.

Kubernetes rolling updateAWS CodeDeploy blue/greenLaunchDarkly
24

Automated health checks + rollback trigger

blocking

The deploy tool itself watches readiness/liveness probes and error rates immediately after cutover — if they fail, it rolls back automatically, before a human even notices.

Kubernetes probesVercel instant rollbackAWS CodeDeploy alarms

PHASE F

Post-deploy

Shipping isn't the finish line — this is what makes sure it actually worked.

25

Production smoke test

blocking

The same value-stream check that ran against staging, run one more time against the real, live production URL.

Playwrightsynthetic monitoring
26

Bake-time monitoring

gate — human watches a window

Watch error rate, latency, and key business metrics for a defined window (commonly 15–60 minutes) before calling the release "done." This is where a canary strategy earns its keep — a spike here aborts the rollout before it reaches 100% of traffic.

DatadogSentryCloudWatch Alarms
27

Team notification

automatic

Who shipped what, when, and whether it's green — so the team has a shared, searchable record without anyone typing it up by hand.

Slack webhookGitHub Deployments API

Grounded in something real

What this project actually has, against the full 27

This project is a solo-built, no-auth, client-only app — the right amount of process for it is nowhere near all 27 steps, and that's a correct engineering call, not a shortcut. The gap column is exactly what you'd add first when this kind of project grows into a multi-user SaaS with real infrastructure behind it.

The honest read: 9 of 27 steps are live and doing real work right now. The rest aren't missing by accident — they're the right next additions in roughly the order a real SaaS would need them, not a checklist to rush through at once.
